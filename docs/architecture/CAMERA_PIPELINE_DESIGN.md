## 0. 요약

온마음은 개인 사용자가 자기 PC 카메라 한 대로 **표정 감정**과 **rPPG 심박**을 함께 재는 앱이다. 두 기능을 한 화면에서 서로 방해하지 않게 돌리기 위한 제안은 다음 다섯 가지다.

1. **측정 하나를 컨트롤러 하나가 책임진다.** 카메라 스트림, 프레임 콜백, 추론, 워커, 버퍼, 세션을 같은 실행 번호(`runId`)로 묶어 시작·중지한다. 재시작 시 루프 중복(F9)과 화면 이탈 시 카메라가 켜진 채 남는 문제를 같은 방식으로 막는다.
2. **프레임은 한 번만 읽고 여러 곳에 나눈다.** 프레임 루프 하나(약 30fps)가 rPPG 샘플링을 매 프레임 하고, 얼굴 검출·표정 분석은 그보다 낮은 주기로 같은 프레임을 쓴다. 부하가 높으면 **표정 주기를 먼저 낮추고 rPPG 샘플링을 지킨다.**
3. **심박 품질이 낮아도 감정 기록은 버리지 않는다.** 두 결과는 따로 저장하고 `sessionId`와 시간으로만 잇는다.
4. **계약을 먼저 정하고 나란히 개발한다.** `RppgResult`의 형식과 시간 규칙을 합의하면, 김우빈(생산자)은 rPPG를, 이정환(소비자)은 Mock 결과로 저장·기준선 계산을 동시에 만든다. 품질 기준값처럼 실측이 필요한 값은 형식과 분리해 나중에 정한다.
5. **검출기·감정 모델 교체는 측정 뒤에 결정한다.** 지금은 현행 face-api + BlazeFace를 유지하고, 실측 결과를 보고 MediaPipe FaceLandmarker 통합과 HSEmotion 교체를 각각 따로 판단한다.

### 1.2 김우빈 rPPG spike

출처: `woobin-01/onmaum`의 `spike/rppg` 브랜치(최신 커밋 2026-10-24 "ME-rPPG 모델을 실험실에 추가해 POS와 나란히 비교"). 팀 레포 Issue #12로 이전할 예정이다. 아래 줄 번호는 그 브랜치 파일 기준이다.

| 파일 | 하는 일 |
|---|---|
| `app/rppg-lab/page.tsx` | `requestVideoFrameCallback`(이하 rVFC)으로 프레임마다 캔버스에 한 번 그려 POS용 ROI 평균 RGB를 모은다(`:401`). face-api(SSD+랜드마크+표정)는 별도 루프에서 ROI 위치만 갱신하고 표정 결과는 쓰지 않는다(`:341`). ME-rPPG는 처리 중인 프레임이 5개 미만일 때만 BlazeFace를 실행해 36×36 크롭을 워커로 보낸다(`:45`, `:372`). 1초마다 BPM을 다시 계산한다(`:441`) |
| `lib/rppg.ts` | POS(Wang 2017), 스펙트럼 피크·SNR, YCbCr 피부색 마스크, 68점 랜드마크 기반 이마·볼 ROI(`:218`). 불규칙한 프레임 시각은 균일 격자로 보간한다(`:35`). 결과는 `{ bpm, snrDb }`(`:11`) |
| `app/rppg-lab/meRppg.worker.ts` | ONNX(`onnxruntime-web`, WASM) 추론. 프레임 1장 + 직전 상태 → BVP 값 1개 + 다음 상태 |

**성능 수치의 범위.** Issue #12의 "30fps, 모델 추론 6~7ms"는 **합성 맥박 영상 기준 보고값**이다.

- 6~7ms는 워커의 `session.run()` 시간만이다(`meRppg.worker.ts:61`). BlazeFace, 캔버스 복사·전처리, 메시지 대기, POS 계산 시간은 들어 있지 않다.
- 표시 FPS는 프레임 콜백 수다. 위 비용들의 영향은 받지만, ME-rPPG에 실제 전달된 프레임 수와는 다르다(처리 중 프레임이 5개면 건너뜀).
- 두 수치 모두 감정 저장·피드백까지 포함한 통합 부하는 아니다. 실행 로그는 아직 공유되지 않았다.

**HSEmotion 설계(`feature/p6-hsemotion`, 2026-06).** face-api 표정넷을 HSEmotion(ONNX)으로 바꾸는 김우빈의 설계다. SSD는 유지하고 **랜드마크넷을 제거**하며, `Fear→sad`, `Contempt→angry` 매핑을 추가한다. 그 문서의 "설계 확정"은 현재 팀 합의가 아니다(7절).

## 3. 측정 생명주기

### 3.1 컨트롤러 하나가 책임진다

지금은 카메라(`CameraView`), 표정 루프(`useEmotionRecorder`), 저장이 각자 자기 상태를 가진다. 여기에 rPPG 루프·워커가 더해지면 시작·중지 순서가 엇갈린다. **측정 컨트롤러** 하나가 아래 자원을 모두 소유하도록 제안한다.

| 자원 | 시작 | 중지 |
|---|---|---|
| 카메라 스트림 | `getUserMedia` | 모든 track `stop()`, `video.srcObject = null` |
| 프레임 콜백 | rVFC 등록 | `cancelVideoFrameCallback`, 실행 번호 확인으로 늦게 온 콜백 무시 |
| 표정 분석 | 저주기 예약 | 예약 취소 |
| rPPG 워커 | 모델 로드(한 번), `reset` | `reset` 전송. 워커 자체는 페이지 동안 재사용 가능 `[합의 필요]` |
| 버퍼 | 빈 버퍼로 시작 | 남은 감정 샘플은 **그 실행의 세션 ID로** flush, RGB·BVP 버퍼는 폐기 |
| 세션 | `startSession` | `endSession(id, reason)` |

**실행 번호(`runId`) 규칙.** 시작할 때마다 새 번호를 만든다. 두 가지를 구분한다.

- **새 실행으로 들어오는 것은 막는다.** 이전 실행의 프레임 콜백·추론 결과가 새 실행의 버퍼·화면에 들어가지 않게, 번호가 다르면 버린다. 공유 boolean 대신 이 번호를 쓰면 F9가 구조적으로 사라진다.
- **이전 실행이 이미 확정한 기록은 끝까지 저장한다.** 중지할 때 만든 마지막 1분 미만 감정 기록과 이미 나온 심박 결과는 시작 시점에 잡아 둔 **이전 세션 ID**로 저장을 마친다. 지금 레코더도 cleanup에서 flush하고(`useEmotionRecorder.ts:128`), 세션 설계도 직전 세션의 늦은 저장을 보존하도록 정했다(`SESSION_DATA_DESIGN.md` 4.4의 3·9번).

**화면 이탈.** 컨트롤러의 정리 함수가 unmount 때도 스트림을 멈춘다. 지금의 스트림 누수를 같은 규칙으로 막는다.

**위치.** 카메라·rPPG 쪽 자원이 대부분이라 생산자 쪽(`features/camera/` 또는 `features/rppg/`) 훅으로 두고, 감정 집계·저장 호출은 지금처럼 주입 가능한 함수로 받는 형태를 제안한다. `[합의 필요: 김우빈 주도, 이정환 공동 검토]`

### 3.2 상태 전이

```text
idle ──시작──▶ starting ──카메라·모델 준비──▶ running ──중지/이탈──▶ stopping ──▶ idle
                 │                              │  ▲
                 └──카메라 오류──▶ error         │  └─얼굴 재검출─┐
                                                └──얼굴 소실──▶ faceLost
```

| 경우 | 처리 제안 |
|---|---|
| 빠른 재시작 (F9) | `stopping`이 끝나기 전 시작 요청이 오면 새 `runId`로 시작한다. 이전 실행의 콜백·추론 결과는 번호로 막고, 이전 실행이 확정한 기록은 이전 세션 ID로 저장을 마친다(3.1) |
| 측정 중 화면 이탈 | 정리 함수에서 스트림·콜백·예약을 모두 멈추고 세션을 닫는다. 지금 `SessionEndReason`은 `'user-stop' \| 'camera-error' \| 'recovered'`뿐이라(`shared/storage/db.ts:20`), 이탈·탭 숨김을 구분하려면 `'page-leave'` 같은 값을 추가해야 한다(저장 계약 변경) `[합의 필요]` |
| 얼굴 소실 | 2초 넘게 얼굴이 없으면 ME-rPPG BVP 버퍼를 비운다(spike `STALE_MS = 2000`, `page.tsx:394`). spike는 이때 **BVP 버퍼만** 비우고 POS RGB 버퍼와 ME-rPPG 모델 상태는 유지한다. 모델 상태도 `reset`해 다시 워밍업할지는 김우빈이 실측으로 정한다 `[합의 필요]` |
| 얼굴 재검출 | 모델 워밍업(spike `ME_WARMUP = 30` 출력, 약 1초) 뒤에도 BPM 계산에는 **최소 6초의 BVP**가 필요하다(`rppg.ts:176`). 그동안은 `status: 'warmup'`, `bpm: null` |
| 카메라 오류 | `error` 상태, 세션은 `endSession(id, 'camera-error')` |
| 모델 하나만 실패 | 2절 표대로 되는 쪽만 계속 |

### 3.3 세션 연결

`SESSION_DATA_DESIGN.md` 4.4에서 정한 규칙을 그대로 따르고, 심박 결과에도 같은 규칙을 적용한다.

- **시작**: `running`에 들어갈 때 `startSession`(내부에서 먼저 `recoverInterruptedSessions` 실행). 반환된 `id`를 컨트롤러가 그 실행 동안 들고 있는다.
- **진행**: 30초마다 `touchSession`(`SESSION_HEARTBEAT_MS`). 감정 저장과 분리해, 얼굴이 없어 저장이 없는 동안에도 세션이 살아 있게 한다.
- **종료**: `endSession(id, reason)`. 마지막 기록의 시각이 `endedAt`보다 조금 늦을 수 있으며 조회·분석에서 허용한다(4.4의 3번). 늦게 도착한 결과를 시각 비교로 버리지 않는다.
- **앱 중단과 복구**: 앱 시작 시 `recoverInterruptedSessions`를 부르고, 반환된 `nextCheckAt`이 있으면 그때 한 번 더 부른다(4.4의 5번).
- **세션 생성 실패**: 측정은 계속하고 감정 기록·심박 결과는 `sessionId` 없이 저장한다(4.4의 6번). 그래서 4.3 타입에서 `sessionId`는 `string | null`이다.
- **생존 갱신 실패**: 기록만 하고 측정·저장에 영향을 주지 않는다(4.4의 7번).

## 4. 시간과 결과 계약

### 4.1 공통 시계

| 값 | 기준 | 쓰는 곳 |
|---|---|---|
| 프레임 캡처 시각 | rVFC `metadata.captureTime` (`performance.now()` 기준 ms) | rPPG 샘플, 표정 샘플 |
| 대체 시각 | `captureTime`이 없을 때 콜백 인자 `now`. **콜백 실행 시각이지 캡처 시각이 아니다** | 위와 같음. 대체 시각을 썼는지 구간별로 표시 |
| 결과 도착 시각 | 워커 응답을 받은 `performance.now()` | 지연 측정에만 사용 |
| 저장 시각 | `performance.timeOrigin + 위 시각`으로 바꾼 `Date` | DB의 `timestamp`, `windowStart`, `windowEnd` |

- **규칙: 저장 시각은 프레임 시각(캡처 시각, 없으면 대체 시각)에서 만든다.** 결과가 도착한 시각으로 저장하면 추론 지연만큼 밀린다.
- 대체 시각은 프레임 표시 지연만큼 실제 캡처보다 늦다. 그 오차가 심박 구간(10초)에 비해 작은지는 12.1 실험에서 확인한다 `[확인 필요]`.
- 감정 샘플도 프레임 시각을 같이 넘기도록 레코더를 바꾼다. 그래야 F4를 고칠 수 있다.

### 4.2 감정 기록의 구간과 유효 시간 (F4)

두 값을 따로 정의한다.

| 값 | 정의 제안 |
|---|---|
| **집계 구간** (시작·끝) | 1분 버킷을 연 시각 ~ flush한 시각. 측정 시작·중지·공백이 버킷을 끊는다. 지금 `timestamp`는 끝 시각만 있다 |
| **유효 감지 시간** | 감지 성공 샘플이 대표하는 시간의 합. 각 샘플은 "자기 프레임 시각부터 다음 샘플 프레임 시각까지"를 대표하되, 한 샘플이 대표하는 시간은 최대 2초로 제한한다(그 이상은 공백으로 본다). 버킷의 마지막 샘플은 flush 시각까지 대표한다 |

- 지금 `duration`은 "유효 감지 시간"의 근삿값으로 쓰이고 있다(일별 집계·최소 5분 판정·감지율). 따라서 **`duration`을 위 유효 감지 시간으로 바꾸고, 집계 구간 시작 시각은 새 필드로 추가**하는 안을 제안한다. 새 필드는 schema 변경이라 v3에서 함께 검토한다 `[합의 필요: 이정환 주도, 김우빈 사전 공유·공동 검토]`.
- 미감지 샘플도 대표 시간을 가진다. `detectionRate = 유효 감지 시간 / 집계 구간 중 공백을 뺀 시간`으로 계산한다.
- 표정 주기가 들쭉날쭉하면 **샘플 수 평균은 짧은 간격 샘플에 무게가 쏠린다.** 대표 시간으로 가중 평균하도록 바꾼다(이정환, `emotionAggregator.ts`).
- 공백 기준: 프레임·샘플 사이가 2초를 넘으면 공백(얼굴 소실 기준과 같음). 넛지의 `MAX_EVAL_GAP_MS`(2분)는 **넛지 평가 사이의 간격** 기준이라 여기에 쓰지 않는다.

### 4.3 `RppgResult` 확장 제안

`SESSION_DATA_DESIGN.md` 3절 초안을 기준으로, 소비자가 구현을 시작하는 데 필요한 항목을 더했다. **`{ bpm, snrDb }`를 품질 단계로 바꾸는 규칙은 생산자(김우빈)가 정한다.** 소비자 쪽에서 SNR을 임의로 점수로 바꾸지 않는다.

```ts
/** 제안 · 미합의. 생산자(features/rppg)가 정의하고 소비자는 type-only import 한다. */
export type RppgStatus = 'ok' | 'warmup' | 'no-face' | 'low-quality'

export interface RppgResult {
  /** 측정 세션 ID. 컨트롤러가 넣는다. 세션 생성에 실패했으면 null (3.3) */
  sessionId: string | null
  /** 실행 식별자(3.1). 세션 ID가 null인 실행끼리도 구분하기 위해 넣는다 */
  runId: string
  /** 같은 runId 안 일련번호. 중복·역순 판별용 */
  seq: number
  /** 추정 구간 (프레임 시각 기준, 4.1) */
  windowStart: Date
  windowEnd: Date
  /** 구간 시각의 출처: 모두 captureTime / 모두 대체 시각(콜백 now) / 섞임 (4.1) */
  timeSource: 'capture' | 'callback' | 'mixed'
  /** status가 'ok'가 아니면 null */
  bpm: number | null
  status: RppgStatus
  /** 품질 단계. 판정 기준은 생산자가 정하고 이 문서에 표로 남긴다 */
  quality: 'good' | 'fair' | 'poor'
  /** 생산자 원값(디버그·재판정용). 소비자는 이 값으로 판정하지 않는다 */
  snrDb: number | null
  /** 구간 길이 중 유효 샘플이 있던 시간의 비율 0~1 */
  validRatio: number
  /** 추정기와 버전. 예: 'pos-forehead-cheeks@1', 'me-rppg@1' */
  method: string
}
```

| 항목 | 제안 | 결정 |
|---|---|---|
| 출력 주기·구간 | 10초 구간을 5초마다 (spike는 1초마다 재계산) | 김우빈 |
| 겹치는 구간의 가중 | 저장·집계할 때 구간 길이가 아니라 **출력 간격(5초)**만큼만 가중해 같은 시간을 두 번 세지 않는다 | 이정환 |
| `qualityScore` | **초안에서 뺀다.** 소비자는 품질 단계만으로 채택 여부를 정하고, 생산자 원값은 `snrDb`로 남는다. 0~1 점수가 따로 필요하다고 생산자가 판단하면 그때 추가한다 | 김우빈 |
| `validRatio` 분모 | 프레임 수가 아니라 **시간** 기준(구간 길이 대비 유효 샘플 시간). 프레임률이 달라도 같은 뜻이 되게 한다 | 공동 |
| `bpm: null`과 상태 | `status !== 'ok'`이면 `bpm === null`. 품질 `poor`는 `ok`이지만 기준선에서 제외 | 공동 |
| 워밍업·실패 이벤트 | 내보낸다. 화면이 "측정 중"을 보여 줄 수 있다. 저장할지는 따로 정한다 | 공동 |
| 중복·역순 | 소비자는 `runId`별로 마지막 `seq`를 기억하고, 같은 `runId`에서 `seq`가 이전 이하이면 버린다. 새 `runId`를 처음 받으면 그 실행의 상태를 새로 만든다 | 이정환 |
| 시각 출처 | `timeSource`로 전달하고 저장한다. 대체 시각 구간의 오차가 크다고 확인되면(12.1) 소비자가 기준선에서 제외할 수 있다 | 생산자 표시, 소비자 정책 |
| POS와 ME-rPPG | 제품에는 **주 추정기 하나**만 쓰고 저장한다. 비교는 실험실 화면에서만 한다. 주 추정기는 12.1 실험실 비교 뒤 결정 | 김우빈 (근거 공유) |
| HRV(IBI) | 1차 범위 제외 (기존 제안 유지) | 공동 |
| 전달 방식 | 컨트롤러가 `onRppgResult(result)` 콜백으로 넘기고, 테스트에서 주입 가능 | 공동 |
| 품질 단계 수·기준값 | 형식은 `good/fair/poor` 3단계, **기준값은 실측 뒤** | 김우빈 |
| `method` 명명 | `추정기@정수 버전`. 계산이 바뀌면 버전을 올린다. 기준선은 `method`별로 따로 낸다 | 공동 |

**계약 PR과 실측 값을 나눈다.** 계약 PR(13절 3번)은 위 표의 **형식**(필드, 의미, 단위, 이벤트 규칙)만 정한다. 품질 기준값, 주 추정기, 출력 주기의 최종값처럼 실측이 필요한 값은 계약 PR 뒤에 정해도 소비자 구현을 막지 않는다.

## 5. 프레임 루프와 부하

### 5.1 구조

```text
카메라 ─▶ [프레임 루프: rVFC, 약 30fps]  ← 컨트롤러 소유 (김우빈)
             │  프레임을 캔버스에 1번 그림
             ├─▶ rPPG 샘플러 (매 프레임): ROI 평균 RGB / 36×36 크롭 → 워커
             └─▶ 저주기 작업 (약 2Hz, 부하에 따라 조절)
                   ├─ 얼굴 검출 + 랜드마크 → rPPG ROI 갱신
                   └─ 표정 분류 → EmotionResult → 감정 집계 (이정환)
```

- **얼굴 검출 결과를 공유한다.** 측정 화면의 face-api와 spike의 face-api를 따로 돌리면 같은 영상에 SSD를 두 번 실행하게 된다. 한 번 실행한 결과로 표정 분류와 POS ROI 갱신을 모두 한다.
- 표정 분석은 지금처럼 `setTimeout` 대기 대신 **프레임 루프에서 "마지막 분석 후 N ms 지났고 이전 분석이 끝났으면" 실행**한다. 실제 주기와 프레임 시각이 기록되므로 F4를 고치기 쉽다.

### 5.2 메인 스레드 예산 (프레임당 약 33ms)

| 작업 | 위치 | 비용 | 근거 |
|---|---|---|---|
| 프레임 캔버스 그리기 + ROI 픽셀 읽기 | 메인 | 미측정 | spike `page.tsx:404` |
| BlazeFace | spike 구현에서는 메인. MediaPipe 공식 가이드는 Face Detector를 워커에서 돌리는 방법도 안내한다 | 미측정 | spike `page.tsx:140` 주석, Google MediaPipe Face Detector 웹 가이드 |
| face-api SSD + 랜드마크 + 표정 | 메인 (tfjs) | 미측정. **세 모델 중 가장 무거울 것으로 추정** | 추정 |
| ME-rPPG 추론 | 워커 | 6~7ms (합성 영상, `session.run()`만) | Issue #12 |
| POS + 스펙트럼 | 메인, 1초마다 | 미측정 | spike `page.tsx:441` |

- **우선순위: rPPG 샘플링 > 표정 분석.** rPPG는 프레임 누락의 정도·패턴에 따라 품질이 떨어질 수 있다(spike는 불규칙 시각을 보간하고 ME 전송을 건너뛰기도 하므로, 어느 정도까지 견디는지는 실측 대상이다). 표정은 1분 집계라 주기를 늦춰도 결과 차이가 작을 것으로 추정한다.
- **두 가지 모드**: 정상 모드는 표정 500ms 주기. 프레임 처리율이 기준 아래로 떨어지면 성능 저하 모드로 바꿔 500ms → 1000ms → 2000ms로 늦춘다. 모드 전환 기준과 각 모드의 합격 기준은 12.3에서 나눠 둔다 `[합의 필요: 기준값]`.
- **워커로 옮길 후보**: POS 계산은 순수 함수라 워커로 옮기기 쉽다. BlazeFace도 워커 실행이 공식 안내되어 있다. face-api(tfjs)를 OffscreenCanvas와 함께 워커에서 돌리는 것은 확인되지 않았다 `[확인 필요]`.
- 이 표의 "미측정"은 12절 검증에서 채운다.

## 8. 상호 간섭

### 8.1 근거

- **말하기·머리 움직임은 rPPG 평가의 대표적인 어려운 조건이다.** PURE 데이터셋은 가만히 앉기, 말하기, 머리 이동을 나눠 녹화해 움직임 강건성 평가에 널리 쓰인다(Stricker 외, 2014). MMPD는 휴대폰 카메라로 정지·머리 회전·말하기·걷기를 담았다(Tang 외, 2023). ME-rPPG 저자 보고(ME-Chunk 설정)에서 교차 데이터셋 MAE는 PURE 0.25 BPM, MMPD 5.38 BPM이다(Wang 외, 2025). 다만 두 데이터셋은 움직임뿐 아니라 조명·피부색·카메라도 다르므로, 이 차이를 말하기·움직임만의 효과로 읽으면 안 된다.
- **말하기가 함께하는 스트레스 상황이 있다.** UBFC-Phys는 휴식·발표·암산 과제로 사회적 스트레스를 유도하며 영상과 손목 BVP를 함께 기록했다(Meziati Sabour 외, 2021). 온마음 사용자가 힘든 순간 중 **말하기가 동반되는 일부 상황**(통화·회의 등)에서는 rPPG 품질이 떨어질 수 있다는 근거로만 쓴다.
- **이마·볼 영역이 얼굴 전체보다 낫다.** 70편을 묶은 체계적 문헌 검토에서 이마와 볼 ROI가 얼굴 전체보다 정확했다(PMC12297079, 2025). spike의 ROI도 말할 때 움직이는 입·턱을 뺀 이마·볼이다(`rppg.ts:218`).
- 원격 진료 조건 평가 연구는 몸 움직임을 제한하지 않으면 **HRV 측정 정확도**가 크게 떨어진다고 보고했다(PMC8704576, 2021). 심박수(BPM)가 아니라 HRV 결과다. 움직임 강건성은 딥러닝 모델 쪽에서 개선이 보고되고 있다(MAR-rPPG, CVPRW 2024).
- 표정 변화 자체가 rPPG에 주는 영향을 따로 분리한 연구는 이번 조사에서 찾지 못했다. 표정은 볼 ROI의 피부를 움직이므로 움직임과 같은 방향의 오차를 낼 것으로 **추정**한다.

### 8.2 책임 나누기

| 할 일 | 담당 |
|---|---|
| BPM 계산, 품질 단계 판정 (움직임·표정 변화량을 품질 판정에 쓸지 포함) | 김우빈 |
| 품질 단계에 따라 저장·추세·기준선·피드백에서 **채택하거나 제외하는 정책** | 이정환 |
| 감정 쪽 정보(표정 급변, 얼굴 이동량)를 rPPG 품질 판정에 넘길지 | 공동 — 1차 범위에서는 넘기지 않고, 품질 판정이 부족하다고 확인되면 검토 |

이정환 쪽 1차 정책 제안: `quality: 'poor'` 결과는 저장하되 기준선·추세 계산에서 제외한다. 화면에는 "측정 상태가 좋지 않았어요"로 구분해 보여 준다.

## 9. 저장과 분석

### 9.1 심박 저장 (v3 초안) `[합의 필요: 이정환 주도, 김우빈 사전 공유·공동 검토, 계약 합의 뒤]`

```ts
// 제안 · 미합의
this.version(3).stores({
  emotions: '++id, timestamp, sessionId',
  sessions: 'id, startedAt, status',
  heartRates: '++id, windowEnd, sessionId',
})
```

- 저장 필드는 4.3의 `RppgResult`에서 `sessionId, windowStart, windowEnd, timeSource, bpm, status, quality, validRatio, method`만. `runId`·`seq`는 중복 제거에만 쓰고 저장하지 않는 것을 제안한다. `snrDb` 저장 여부는 생산자와 정한다.
- 4.2의 감정 기록 집계 구간 시작 시각 필드도 같은 v3에서 검토한다.
- 저장량: 5초마다 1건이면 1시간 720건. 한 건 약 150바이트로 하루 8시간 약 0.9MB(`SESSION_DATA_DESIGN.md` 4.6 추정).
- **기존 API 확장 필수**: `getPersonalRecordsByRange`, `exportPersonalData`(`schemaVersion` 3), `deleteAllPersonalData`, 측정 중 삭제 차단(`isMeasurementActive`)에 `heartRates`를 넣는다.

### 9.2 심박 기준선과 비교

- **품질 조건을 통과한 구간만** 쓴다: `status: 'ok'`, `quality`가 `good` 또는 `fair`, `validRatio ≥ 0.7` `[합의 필요]`. 이 조건은 신호 품질만 보며 **안정(휴식) 상태를 판별하지 않는다.** 활동 중 심박이 섞이는 문제는 1차에서 받아들이고, 안정 상태 판정이 필요하면 별도로 검토한다.
- 감정 기준선과 같은 방식을 쓴다. 현재 감정 기준선은 **오늘을 뺀 지난 13개 달력 날짜 중 유효일(하루 5분 이상)이 3일 이상이면 그 값들의 중앙값**이다(`features/algorithm/baseline/baseline.ts:11`–`13`, `:30`). 심박도 하루 유효 시간 5분 이상인 날을 유효일로 보고, 유효일이 3일 미만이면 "평소 대비"를 보여 주지 않는다 `[합의 필요: 최소 시간]`.
- 기준선은 `method`별로 따로 낸다. 추정기가 바뀌면 새 기준선이 쌓일 때까지 "평소 대비"를 보여 주지 않는다.

### 9.3 감정과 심박을 함께 쓰는 방식

- **1차: 나란히 보여 주기.** 하루·시간대별 스트레스 지수 옆에 "평소 대비 심박 변화"를 같이 보여 준다.
- **결합 지표(감정 + 심박으로 만든 새 점수)는 만들지 않는다.** 실제 사용자 데이터와 자기보고(체크인)로 검증한 뒤 검토한다.
- 피드백(⑥)은 지금 규칙(감정 기반)을 유지하고, 심박은 근거 문구에만 보조로 쓴다. 예: "오후에 스트레스가 높았고, 심박도 평소보다 높았어요."
- 의료적 해석(부정맥, 고혈압 등)은 쓰지 않는다.

"영구 저장하지 않음"과 "측정 중 메모리에 잠시 보유"를 나눈다.

|---|---|---|
| 영상 프레임 | 캔버스 1장, 다음 프레임에 덮어씀 | 안 함 |
| 얼굴 크롭 (36×36) | 워커로 넘긴 뒤 추론하고 버림 | 안 함 |

| BVP 파형 | 최근 약 12초 보관, 계산은 최근 10초 (spike `page.tsx:275`, `rppg.ts:169`) | 안 함 |

- 모든 처리는 기기 안에서 한다. 모델·WASM은 자체 서빙한다(Issue #12의 `public/vendor/` 방식).
- **실험실 기준 센서 데이터**: spike는 `localStorage`의 `onmaum_rppg_lab_rows`에 넣는다. 팀 앱과 같은 origin으로 옮기면, 현재 구현은 `onmaum_` 접두어 키를 모두 모으므로 **이미 전체 삭제 대상이고 JSON 내보내기에도 들어간다**(`shared/storage/personalData.ts:66`, `:86`, `:169`). 키 이름을 바꾸거나 예외를 두어도 같은 origin의 `localStorage`에 남는 것은 같으므로, 기존 제안("기준 센서 데이터는 앱 저장소에 넣지 않는다")을 다음처럼 정확히 좁힐 것을 제안한다 `[합의 필요]`.
  - 실험 데이터는 기기 안(같은 origin)에 두되 **일반 개인 기록 내보내기에서는 제외**하고, 실험실 화면에 별도 내보내기(CSV 등)와 삭제 버튼을 둔다.
  - 사용자의 "전체 삭제"에는 **포함**한다. 기기에 남은 내 데이터를 모두 지운다는 기대에 맞추기 위해서다.
  - 이를 위해 실험 키를 `PREFERENCE_KEYS`처럼 별도 목록으로 관리하고, `exportPersonalData`에서만 빼는 예외를 둔다(이정환, `personalData.ts`).

## 11. 백그라운드 동작

- 브라우저는 숨긴 탭에서 `requestAnimationFrame`을 멈추고 타이머를 늦춘다(MDN Page Visibility API).
- rVFC가 숨긴 탭에서 어떻게 동작하는지는 명세에서 확인하지 못했다. WebKit에는 창이 숨겨지면 rVFC 콜백이 오지 않는 버그 보고가 있었고 수정되었다(WebKit Bug 282797). Chrome 동작은 **확인 필요**다.
- 따라서 웹에서는 **"탭을 띄워 둔 동안만 측정"**을 기본으로 하고, 탭이 숨겨지면 세션을 끊는다(3.2). 백그라운드 측정은 Electron(김우빈 ②)에서 다룬다. Electron은 창별 백그라운드 쓰로틀링을 끄는 설정이 있어 후보가 된다 `[확인 필요: 김우빈]`.

### 12.2 정확도

- 조건: 조용히 / 말하기 / 머리 움직임. 가능하면 스트레스 과제(UBFC-Phys처럼 암산) 조건 추가.
- 기준값: 스마트워치·손가락 센서. spike는 사람이 BPM을 손으로 입력한다(`page.tsx:485`). **입력 지연**과 **비교 구간 정렬**(입력 시각 기준 ±5초 등)을 검증 항목에 넣는다.
- 지표 정의:
  - **MAE**: 품질 기준을 통과한 결과만의 평균 절대 오차(spike의 `gatedMae`).
  - **유효 결과 비율**: 측정 시간 중 품질 기준을 통과한 결과가 덮는 시간의 비율. spike의 `coverage`는 수동 입력 행 중 통과 비율(`rppg.ts:277`–`291`)이라 이것과 다르다. 실험실에서도 시간 기준 비율을 따로 계산한다.
  - 품질 기준으로 결과를 많이 버리면 MAE는 좋아지지만 쓸 수 있는 시간이 줄어든다. 두 값을 항상 함께 본다.
